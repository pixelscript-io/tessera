# Releases

This page records what each release and milestone delivered, newest first. The current release is 0.9.0; see [Versioning](#versioning) for what a version number means here. `tessera diff --changelog` generates a section from any two versions.

## v0.1 (in progress)

- **Published:** `@pixelscriptio/tessera` and `@pixelscriptio/create-tessera` 0.1.0 are on npm; 0.2.0 adds Milestones 13 to 15, and 0.2.1 adds Milestone 16, 0.2.2 ships the Prettier plugin and `tessera format`, 0.3.0 adds the system manager, 0.4.0 adds the tessera preset, 0.4.1 restyles the docs and the preset page after the site design, and 0.5.0 adds the items below.
- **0.9.0: Tessera UI is a catalogue you copy from, and a project has design systems.** The component library stops being a package and becomes a registry, like shadcn: `npx tessera add Button` copies a component into `system/components`, where it is yours to change. The registry is served from tessera-ui.pixelscript.io, which also lists every component with its contract, tokens and docs ([Tessera UI](/guide/tessera-ui)). `add` brings the components a component uses, tells you which npm packages it needs (`--install` installs them), refuses one that needs a newer Tessera, records what it installed in `tessera.lock.json`, and asks what to do when a name is taken (`--replace`, `--as`, `--diff`, `--list`, `--from` for a folder or another registry). Before it writes a component it compares the tokens it uses with each of your design systems and reports the ones that are missing or of the wrong type, with three fixes: `--fit add` writes the missing tokens in a file of their own, `--map from=to` rewrites the component to tokens you have, and `--fit set` installs a whole token set. Afterwards it runs the check on what it wrote. A project can have several design systems, each in `system/<name>/tokens` with the components shared in `system/components`; `systems` and `defaultSystem` in `tessera.config.ts` name them, and the docs have a switcher. `tessera dev` now serves the app and the docs together, each on its own port (`docs: false` turns the docs off), and `tessera a11y --system all` tests the components in every system. There are two presets, `tailwind` and `unstyled`, with the same starter app and two copied components (Button and Card); the Tessera look is a token set you add (`tessera add tokens:tessera`). A TypeScript `tessera.config.ts` in a package that is not `"type": "module"` is compiled instead of imported by Node, because Node 24.22 can crash on a second import.

  **Breaking:** `@pixelscriptio/tessera-ui` is not published any more. A project that lists it should remove it and run `npx tessera add` for the components it uses (`npx tessera add --list` shows them all); a component of the same name in `system/components` is the one used, so nothing changes until you do. `tessera eject` is removed (a component you add is already a copy), and a project no longer needs `@pixelscriptio/tessera-ui` in `package.json` to use the library components. Tokens move from `system/tokens` to `system/<name>/tokens` for a project made by `init`; an existing project that keeps `system/tokens` and has no `systems` in its config works as before. The presets are renamed: `--preset tessera` is gone (start with `tailwind` and run `tessera add tokens:tessera`) and `--preset none` is now `unstyled`; `init` says so. `create-tessera` and the Quick start install one package, `@pixelscriptio/tessera`.

- **0.8.0: Tessera UI, a component library.** A new package, `@pixelscriptio/tessera-ui`, ships 26 accessible, themeable components as `.tess` source: the nine the presets used to copy into a project (Accordion, Button, Checkbox, Combobox, Dialog, Select, Switch, TextField), and new Alert, Avatar, Form, FormField, Icon (from Lucide, a dependency of the library only), Kbd, Popover, Progress, RadioGroup, Separator, Skeleton, Spinner, Textarea and Tooltip. See [Tessera UI](/guide/tessera-ui). A component in your project with the same name replaces the library's, and `tessera eject <Name>` copies one to start from. A new `radio-group` behavior joins the other six. The contract has a new `preview` field (sample props and slot content) that the design system docs, the generated accessibility tests and the usage examples AI tools read all use, so every component shows itself fully. The docs app has a new look. The `tessera` preset has squarer corners, a flatter shadow and 14px control text. Versioning is written down: Tessera stays at 0.x, a minor may break and says so, and the three packages share one number ([Versioning](#versioning)).

  **Breaking:** `tessera init` no longer copies Button, Checkbox and the other library components into `system/components` for the `tessera` and `tailwind` presets: it adds `@pixelscriptio/tessera-ui` as a dependency instead (and still writes Card and Badge). An existing project keeps the copies it has; a copy with a library component's name replaces it, so nothing changes until you delete one. The Quick start installs both packages: `npm install @pixelscriptio/tessera@latest @pixelscriptio/tessera-ui@latest`. A project uses the library only if its `package.json` lists it and it has design tokens. The generated accessibility test file no longer has `fixtures`: a component's contract says what to show it with.

- **0.7.0: the rest of the security findings.** An API forgets everything it remembers when its `headers`, `credentials` or `base` change, so a different person is not answered from the last one's memory. A path value of `.` or `..` is refused (a read shows an error, a write rejects). `tessera api import` writes the server address so that nothing in it can end the string, and refuses a download over 10 MB. **Breaking for the accessibility tests:** they now need Vitest 4.1.12 or newer with `@vitest/browser-playwright` (older Vitest versions have known vulnerabilities); `tessera a11y` sets that up, and a project that already has a Vitest configuration keeps it, so a project on Vitest 3 should upgrade. See [Security](/guide/security).
- **0.6.8: security and a faster command line.** A [security guide](/guide/security) says what Tessera protects and what stays yours. `navigate()` rejects `javascript:` and other non-http addresses; the renderer replaces a `javascript:` address in `href`, `src`, `action`, `formaction` and `poster` with `about:blank`, and ignores `onclick`-style attributes; an API sends its headers and credentials only to its own origin (`allowOtherOrigins` to change that); and the files `init` writes for AI tools run Tessera as `npx @pixelscriptio/tessera` (or `npm run`), because a bare `npx tessera` can download an unrelated package when Tessera is not installed. Every command except `dev`, `build`, `preview`, `docs` and `elements` no longer loads Vite, and a `tessera.config.ts` is imported by Node itself where it can read TypeScript: `help` takes about 130 ms instead of 350, and `check` about 215 instead of 440. A config file can now import its neighbours.
- **0.6.7: a comparison page, and links to a place on a page.** The landing page has a [comparison](https://tessera.pixelscript.io/compare) of Tessera with React, Vue and Svelte, including what Tessera does not have. The router now scrolls to the element named by the hash when an app starts on an address that has one (`/#data`); before, only a navigation after the app started did.
- **0.6.6: a new project is ready for an AI tool.** `tessera init` (and `npm create @pixelscriptio/tessera@latest`) writes `AGENTS.md` and `llms.txt` for every preset, a `CLAUDE.md` that imports `AGENTS.md` (Claude Code reads that name), and a `.mcp.json` that starts `tessera mcp`. `AGENTS.md` now teaches the language itself: a component, the template syntax, tokens in styles, pages, data and shared state, with samples that are compiled in CI. The whole documentation ships in the package as one Markdown file (`node_modules/@pixelscriptio/tessera/dist/docs/llms-full.txt`) for a model to search offline, and the docs site serves `/llms.txt` and `/llms-full.txt`. See [AI coding tools](/guide/agents).
- **0.6.5: sharing state.** A script file in `app/state` is shared state, named after the file and usable in every `.tess` file without an import: `{cart.count}` reads a signal, `cart.add(item)` calls a function, and destructuring keeps it reactive. A member that is not in the file is an error with a suggestion (T5012), and state is read-only outside its file (T5011), so every change is in one place. The tutorial has a step for it ([Sharing state](/tutorial/09-shared-state)), the kitchen-sink app has a `cart`, `.tessera/state.d.ts` types it, the manifest, `AGENTS.md`, `llms.txt` and the MCP tools `list_state` and `get_state` list it, and the landing page has a section. The tutorial has eleven steps now: Accessibility and Checking are steps 10 and 11. See [Sharing state](/guide/shared-state). Saving it in the browser and the address, state for part of a page, and the read and write graph follow.
- **0.6.0: fetching data.** `get`, `post`, `put`, `patch` and `del` in `@pixelscriptio/tessera/core`: reads that follow signals, share one answer, cancel what nobody waits for and retry; writes that say when they are working and refresh the reads they affect. See [Fetching data](/guide/data). In `.tess` files they need no import and a template reads their results directly, with a warning (W4105) for a template that never shows loading or errors; and a file in `app/apis` is an API, named after the file, so an app can call several servers. An API description (`app/apis/<name>.api.json`, or made by `tessera api import` from OpenAPI) lets the compiler check endpoints, parameters and the fields a template reads (T5006 to T5009), and gives AI tools the endpoints (`list_apis`, `get_endpoint`). The default `tessera` preset page lists data from an API, and the tutorial has a data step. Optimistic updates and data for pages follow.
- **0.5.1: the landing page and what it needed.** The public landing page is a Tessera app (`landing/` in the repository), the first real one. For it, templates gained SVG (`<svg>` and its tree are created as SVG) and `ref="name"`, which holds an element in a `state()`; and there is a `tabs` behavior with a conformance suite ([Behaviors](/guide/behaviors)).
- **0.5.0: lint, elements, prerendering and the accessibility suite for users.** `tessera lint` checks the CSS of any project against your tokens ([Linting any project](/guide/lint)); `tessera elements` builds the design system as custom elements with React wrappers ([Custom elements](/guide/elements)); `tessera build --prerender` writes static HTML for pages; `tessera a11y` and `@pixelscriptio/tessera/a11y` ship the generated accessibility tests to your project ([Accessibility](/tutorial/10-accessibility)); new components (Checkbox, Switch, Accordion, TextField, Dialog, Combobox, Select) and behaviors (toggle, disclosure, dialog, combobox) come with the `tessera` and `tailwind` presets ([Behaviors](/guide/behaviors)); the command line has a new look.
- **Milestone 20: the `tessera` preset, and docs styled by your tokens.** `tessera init` has a third starting point, `tessera` (a small design system of our own, now the default), next to `tailwind` and `none`. The generated docs are styled from the project's semantic tokens, so the app and its docs share one set of token files; a project without tokens gets a built-in look. The docs also look different: warm paper neutrals, one green accent, soft rounded corners. See [Starter presets](/guide/presets).
- **Milestone 19: token import and export in the docs.** The docs app has an **Export** page (DTCG or Tokens Studio files, as a zip or one by one), and `tessera docs --edit` adds **Bring in tokens**, for people who do not write code. An import is validated by the compiler on a copy of the project first and previewed as a diff with its breaking/additive classification; one-step undo; a branch and commit to propose the change. Tokens stay edited in your design tool; components are not edited from the docs. See [Tokens in the design system docs](/guide/system-manager).
- **Formatting.** The Prettier plugin now ships in the package (`@pixelscriptio/tessera/prettier`); `tessera init` writes its configuration; `tessera format` formats `.tess` files without any editor, with `--check` for CI and `--stdin-filepath` for editors that call an external formatter.
- **Milestone 16: versioning and codemods.** `tessera diff <ref>` classifies changes as breaking, additive or cosmetic (a contrast flip or a token moving past its neighbour in a scale is breaking) and can print a changelog section; contracts and tokens can say what was deprecated or renamed, and the compiler warns or says what it became; `tessera codemod` rewrites the uses of a rename; `tessera report` lists remaining uses of deprecated and renamed things. ## Versioning

Tessera is at 0.x and will stay there for a long time. The version says how a release may affect you; it does not say how close the project is to finished.

- **The number is `0.MINOR.PATCH`, and the minor keeps counting.** After 0.9 comes 0.10, then 0.11. These are numbers, not decimals, and every tool orders them correctly. A minor does not mean "closer to 1.0".
- **A minor release adds things, and may change or remove things.** Under semver, 0.x makes no compatibility promise, and a minor is where a break may happen. Every break is listed under "Breaking" in the release notes, with how to update, and with a codemod when a codemod can do it (`tessera diff --changelog` and `tessera codemod`).
- **A patch release only fixes.** It does not break anything and adds no feature you must learn.
- **The two packages move together.** `@pixelscriptio/tessera` and `@pixelscriptio/create-tessera` always have the same number. The Tessera UI catalogue is not a package and has no number of its own: each item in the registry says the oldest Tessera it works with (`minTessera`), and `tessera add` refuses it on an older one. A project's `^0.9.0` takes patches but never a new minor by itself.
- **1.0 is a promise, and it is not scheduled.** It will be declared, by the author, when all of these are true: the contract and token formats and the public API are stable, with the deprecation window enforced by the tools; the component library has the components it set out to have, tested for accessibility; server rendering has hydration; the security audit has been repeated and its findings fixed; and real projects have run on it through at least one breaking minor with the codemods. Until then no release is called 1.0, a beta or a release candidate.
- **The number cannot run out.** A minor can be 10, 50 or 200: 0.10.0 follows 0.9.0, and nothing makes 1.0 the next release. Publishing is guarded: each published package runs `scripts/check-version.mjs` before it publishes, and a version that is not `0.MINOR.PATCH` stops the publish, with no flag to skip it. Only the author changes that, when declaring 1.0.

A test (`packages/tessera/test/versions.test.ts`) checks that the three numbers match, that they are `0.MINOR.PATCH`, and that the library's peer range names the same minor.
